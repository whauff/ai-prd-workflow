# ai-prd-workflow 团队使用说明

这份说明给团队成员使用。它说明什么时候用这套 skill、怎么向 Codex 提需求、产出后检查什么。

## 什么时候用

适合使用：

- 新需求需要收口成可评审交付。
- 早期想法或方案需要先被挑战、找漏洞或判断是否值得继续。
- PRD、原型、规则稿、流程图需要统一组织。
- 已有原型需要评审前收口。
- 多个交付物需要总目录、项目目录和更新记录。
- 需求后续还会迭代，需要保留过程和版本追溯。

不适合使用：

- 只需要技术实现方案、接口设计或数据表设计。
- 业务规则、权限或状态还没有任何上下文，却要求直接写完整 PRD。
- 只想做视觉创意、营销页或正式前端工程。
- 希望把某一期页面样式机械套到所有页面。

## 常用说法

### 需求收口

```text
用 ai-prd-workflow 帮我把这个需求收口成可评审交付。
```

适用于需求还比较散，需要先判断是否要澄清、Brief、PRD、原型、规则稿或流程图。

### 想法拷问

```text
用 grill-me 先拷问一下这个想法，看看最脆弱的假设和下一步验证动作。
```

适用于想法还早、方案看起来自洽但未验证、或团队已经倾向推进前需要先找漏洞时。

### 先定口径

```text
用 review-brief 先确认范围、判断顺序、字段层级、权限和待拍板问题。
```

适用于大家还没对齐范围、顺序、状态、字段或多端权限时。

### 生成原型

```text
用 build-prototype 基于当前 PRD 做可评审原型，重点覆盖页面结构、关键状态和交互。
```

适用于页面、表单、状态或交互本身会影响评审结论时。

### 移动端原型收口

```text
用 review-prototype 按移动端业务作业页标准收口这个原型。
```

适用于小程序、员工端、门店端、医生端等移动作业页面。重点检查轻结构、短文案、真实用户视角、状态和主动作分层。

### 后台原型收口

```text
用 review-prototype 按后台结构原型标准检查这个页面。
```

适用于配置页、列表页、审核页、详情页、运营处理页和规则管理页。重点检查结构、扫描比较、字段职责和列表副文案克制。

### 目录页收口

```text
用 review-prototype 按交付目录页标准整理总目录和项目目录。
```

适用于总目录、项目目录、评审导航页和交付入口页。重点检查两层入口、固定中文命名、评审顺序、更新记录和状态版本同步。

## 三类复用标准

### 移动端业务作业页

适用范围：

- 小程序
- 员工端
- 门店端
- 医生端
- 其他移动业务作业页面

复用重点：

- 真实用户看不到的评审解释不进入页面本体。
- 页面优先表达当前状态、关键字段和下一步动作。
- 模块标题稳定，不随结果状态变化而改名。
- 短文案、轻结构、明显主动作和移动端可点击区域优先。

### 后台结构原型

适用范围：

- 配置页
- 列表页
- 审核页
- 详情页
- 运营处理页
- 规则管理页

复用重点：

- 后台优先解决结构、扫描、比较和处理效率。
- 列表页不写解释型副文案。
- 筛选、表格、详情、操作区职责分清。
- 同类页面和状态保持同一骨架。

### 交付目录页

适用范围：

- 总目录
- 项目目录
- 评审导航页
- 交付入口页

复用重点：

- 总目录只做项目索引。
- 项目目录承载评审入口和更新记录。
- 链接使用固定中文名称，不暴露原始文件名。
- 原型、PRD、流程图、状态或版本变化后，登记可追溯更新记录。

## 交付检查

完成一次需求交付前，至少检查：

- 是否有清晰的总目录或项目目录入口。
- 项目目录是否包含最近更新、版本、状态、评审顺序和更新记录。
- PRD、原型、规则稿、流程图等正式入口是否指向最终版本。
- 链接名称是否是中文可读名称，而不是原始文件名。
- 状态、版本、最近更新时间和更新记录是否一致。
- 原型页面内是否混入评审解释、重复说明或无意义装饰。
- 移动端和后台是否分别符合对应页面标准。

## 使用边界

不要让这套 skill 做这些事：

- 直接脑补业务规则。
- 写后端接口、数据库表、研发实现方案。
- 把原型当成正式开发代码承诺。
- 为了好看牺牲评审效率。
- 把某一期页面样式当成所有需求的固定模板。

## 团队协作建议

- 需求早期先用 `ai-prd-workflow` 判断交付物组合。
- 想法还早但已经想推进时，先用 `grill-me` 压力测试。
- 口径没定时先用 `review-brief`，不要直接写长 PRD。
- 原型先用 `build-prototype` 表达结构、状态和交互。
- 原型稳定后再用 `review-prototype` 做评审前收口。
- 每次改动影响评审理解、状态、版本或入口时，都要更新项目目录页的更新记录。
