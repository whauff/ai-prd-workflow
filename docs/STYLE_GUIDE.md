# ai-prd-workflow 原型交付质量说明

这份说明用于帮助团队理解：为什么原型交付质量统一要单独做，而不是混在原型结构设计里。

这里的设计质量要求服务于 PRD 交付，不改变主流程优先级；原型只是当页面、状态或交互影响评审时才出现的辅助交付物。

## 目标

把“原型做出来”与“原型达到统一交付标准”拆成两个阶段：

1. `build-prototype`
   - 解决结构、页面、交互、状态覆盖
2. `style-prototype`
   - 解决视觉统一、响应式适配、状态表达、可用性和文案清晰度

## 为什么要拆开

- 不同同事的视觉习惯差异很大
- 结构还没稳定时就做样式统一，返工成本高
- 团队真正需要的是稳定标准，而不是每次重新定义美学方向

## 什么时候进入 style-prototype

- 原型主要页面已经出来了
- 当前评审问题集中在“看起来不统一”、适配不稳、状态不完整或交付质感不稳定
- 准备把原型发给更多同事、业务方或跨团队对象评审

## 什么时候不要进入 style-prototype

- 需求还在变，页面结构还在大改
- 只是为了好看，实际上并不影响评审
- 现在真正缺的是规则、流程或 PRD，不是原型交付质量

## 统一什么，不统一什么

### 要统一

- 字体层级
- 布局与间距
- 按钮和表单样式
- 颜色语义
- 空状态、错误态、加载态、禁用态
- 响应式适配、长文本、可点击区域和基础可访问性

### 不在这里统一

- 品牌创意方向
- 个性化视觉实验
- 正式开发级前端工程方案
- 业务逻辑和页面信息架构
