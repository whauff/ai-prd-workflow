# ai-prd-workflow 原型交付质量说明

这份说明用于帮助团队理解：为什么原型评审前收口要单独做，而不是混在原型结构设计里。

这里的设计质量要求服务于 PRD 交付，不改变主流程优先级；原型只是当页面、状态或交互影响评审时才出现的辅助交付物。

## 目标

把“原型做出来”与“原型收成可评审版本”拆成两个阶段：

1. `build-prototype`
   - 解决结构、页面、交互、状态覆盖
2. `review-prototype`
   - 解决页面减法、视觉层级、响应式适配、状态表达、按钮可点击性和文案清晰度

## 为什么要拆开

- 不同同事的视觉习惯差异很大
- 结构还没稳定时就做样式统一，返工成本高
- 团队真正需要的是稳定标准，而不是每次重新定义美学方向

## 什么时候进入 review-prototype

- 原型主要页面已经出来了
- 当前评审问题集中在页面太重、入口不明显、适配不稳、状态不完整或交付质感不稳定
- 准备把原型发给更多同事、业务方或跨团队对象评审

## 什么时候不要进入 review-prototype

- 需求还在变，页面结构还在大改
- 只是为了好看，实际上并不影响评审
- 现在真正缺的是规则、流程或 PRD，不是原型交付质量

## 统一什么，不统一什么

### 要统一

- 字体层级
- 布局与间距
- 按钮和表单样式
- 颜色语义
- 空状态、错误态、加载态、禁用态
- 响应式适配、长文本、可点击区域和基础可访问性

### 不在这里统一

- 品牌创意方向
- 个性化视觉实验
- 正式开发级前端工程方案
- 业务逻辑和页面信息架构

## 可复用场景

这套原型收口标准可以复用到三类常见交付：

### 移动端业务作业页

适用于小程序、员工端、门店端、医生端和其他移动作业页面。

复用重点：

- 真实用户看不到的评审解释，不进入页面本体。
- 页面优先表达当前状态、关键字段和下一步动作。
- 模块标题稳定，不随结果状态变化而改名。
- 短文案、轻结构、明显主动作和移动端可点击区域优先。

对应运行时参考：

- `skills/ai-prd-workflow/review-prototype/references/mobile-business-page.md`

### 后台结构原型

适用于配置页、列表页、审核页、详情页、运营处理页和规则管理页。

复用重点：

- 后台优先解决结构、扫描、比较和处理效率。
- 列表页不写解释型副文案。
- 筛选、表格、详情、操作区职责分清。
- 同类页面和状态保持同一骨架。

对应运行时参考：

- `skills/ai-prd-workflow/review-prototype/references/admin-structure-page.md`

### 交付目录页

适用于总目录、项目目录、评审导航页和交付入口页。

复用重点：

- 总目录只做项目索引。
- 项目目录承载评审入口和更新记录。
- 链接使用固定中文名称，不暴露原始文件名。
- 原型、PRD、流程图、状态或版本变化后，登记可追溯更新记录。

对应运行时参考：

- `skills/ai-prd-workflow/review-prototype/references/delivery-index-page.md`
