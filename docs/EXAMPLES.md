# ai-prd-workflow examples

这份示例用于帮助第一次接触这套 skill 的同事快速判断：当前需求应该从哪个入口开始。

## 示例 1：从模糊想法到 PRD

### 输入

“我们想做一个小程序状态检查能力，避免门店提交错误配置，但现在还没想清楚哪些状态要拦、哪些只提醒。”

### 推荐入口

1. `ai-prd-workflow`
2. `clarify-requirement`
3. `write-prd`
4. `write-rules`

### 原因

- 需求目标和边界还不够清楚
- 后续大概率存在规则判断口径

## 示例 2：需求已经明确，只差文档沉淀

### 输入

“需求已经讨论完了，帮我整理成一版可以评审的 PRD，重点是背景、目标、用户场景和验收标准。”

### 推荐入口

1. `write-prd`

### 原因

- 不需要额外澄清
- 当前核心产物就是 PRD

## 示例 3：界面是争议焦点

### 输入

“PRD 已经有了，但大家对页面上的状态提示、按钮文案和异常反馈意见很多，想先看一个可评审原型。”

### 推荐入口

1. `build-prototype`
2. `style-prototype`
3. 必要时回写 `write-prd`

### 原因

- 当前争议集中在交互而不是需求背景

## 示例 3.1：结构没问题，但交付样式不统一

### 输入

“原型已经做出来了，但不同页面的字级、按钮、间距、空状态都不统一，想整理成可以反复评审的标准版。”

### 推荐入口

1. `style-prototype`

### 原因

- 当前问题不在结构，而在交付标准不一致

## 示例 4：规则比页面更重要

### 输入

“需要定义哪些地址算异常、哪些只提示优化，避免误伤真实门店。”

### 推荐入口

1. `write-rules`
2. 如规则前提还不清楚，先补 `clarify-requirement`

### 原因

- 当前协作重点是判断口径和边界样本

## 示例 5：逻辑链路复杂，文字说不清

### 输入

“保存前会做校验，保存后还要同步、回写、处理异常，评审时总有人理解不一样。”

### 推荐入口

1. `make-flowchart`
2. 如流程图影响方案理解，再同步 `write-prd`

### 原因

- 当前问题在于逻辑分支表达不清
