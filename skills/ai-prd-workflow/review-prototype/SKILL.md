# review-prototype

把已有原型收成可评审版本。它承接 `build-prototype` 之后的阶段：结构和关键交互已经存在，现在检查页面是否清楚、克制、一致、可追溯。

## 读取文件

开始修改前读取：

- [references/prototype-review-checklist.md](references/prototype-review-checklist.md)

按页面类型继续读取：

- 移动端、小程序、员工端、门店端、医生端或其他移动作业页面：读 [references/mobile-business-page.md](references/mobile-business-page.md)
- 后台、管理端、配置页、列表页、审核页或运营处理页：读 [references/admin-structure-page.md](references/admin-structure-page.md)
- 总目录页、项目目录页、评审导航页或交付入口页：读 [references/delivery-index-page.md](references/delivery-index-page.md)

如果属于 `ai-prd-workflow` 项目，同时尊重 Brief / PRD / 规则稿边界。若页面职责、字段层级、状态口径或业务规则仍不清楚，先回到 `review-brief` 或对应交付物，不直接用视觉调整替用户拍板。

## 适用场景

- 原型已有页面结构，但视觉层级、按钮、状态、间距或文案显得散。
- 用户在评审中指出页面太重、太乱、太丑、说明太多、入口不明显、同类页面不一致。
- 需要把原型从“能看”收成“可评审、可追溯、可交付”。
- 需要将移动端、后台或交付目录页按团队已沉淀的原型标准做复用检查。
- 原型改动后需要同步项目目录页的更新记录。

不适用：

- 从零搭原型。使用 `build-prototype`。
- PRD、规则、流程图口径未定。回到上游。
- 生产级前端工程、组件库或设计系统建设。

## 工作方式

1. 识别目标原型文件、平台、页面类型和本轮评审问题。
2. 判断原型结构是否稳定。若问题本质是业务口径或页面职责不清，先说明影响范围并回到上游确认。
3. 先分类再动手：
   - `structure`: 页面骨架、模块顺序、重复信息、状态布局
   - `style`: 字体、间距、颜色、边框、视觉重量
   - `state`: 空、错、禁用、加载、完成、阻塞、无权限
   - `action`: 按钮、链接、可点击区域、hover/focus、主次动作
   - `copy`: 标签、说明、重复解释、动作文案
4. 做减法优先：删除无决策价值的解释、重复文案、过重装饰和伪按钮。
5. 同一页面或同类页面中成组修正，不只修截图里被指出的一个点。
6. 统一字体层级、间距节奏、颜色语义、按钮层级、表单控件和状态表达，但不借机重做业务。
7. 检查响应式、长文本、空数据、密集数据、焦点可见性、文本截断和布局错位。
8. 保留原型辅助层的必要入口，例如目录、摘要、热区；但辅助层不能压过业务页面。
9. 若本轮变化影响评审理解、状态表达、导航、版本或可追溯性，更新项目目录页 `index.html` 的更新记录。

## 硬规则

- 不改变业务规则、权限范围、判断顺序、页面职责或验收标准。
- 不发明新模块、新状态、新能力、新标签或新说明，除非 PRD、规则稿、现有产品样例或用户明确支持。
- 不把评审解释塞进页面本体；评审辅助信息放目录、摘要、旁注、README 或更新记录。
- 不做作品集式视觉，不追求炫技，不为了好看牺牲评审效率。
- 不创建独立设计系统；只在当前原型范围内收口一致性。
- 不把单个截图当全部问题；先横向扫同类问题。

## 输出

完成后说明：

- 收口了哪些原型页面或页面区域。
- 做了哪些减法、层级、状态、按钮或文案调整。
- 哪些内容刻意没有改，因为涉及业务口径或超出本轮范围。
- 是否检查了响应式、长文本、空/错/禁用等边界。
- 项目目录页更新记录是否已登记；未登记则说明原因。
