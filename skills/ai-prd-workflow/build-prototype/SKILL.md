# build-prototype

只做产品交付原型，帮助评审页面结构、关键状态和交互路径。

## 前提

只有在以下条件至少满足大部分时才进入本技能：

- 需求目标已经基本清楚
- 核心用户和场景已经清楚
- 主要页面或关键操作路径已经有初步定义

页面目标不清时，先回到澄清或 PRD。

若已有 Brief，以 Brief 为口径基准，不改范围、顺序、字段、权限或拍板结论。

## 读取文件

开始产出前按需读取：

- [../shared/references/prototype-guidelines.md](../shared/references/prototype-guidelines.md)
- [../shared/references/prototype-design-quality.md](../shared/references/prototype-design-quality.md)
- [../shared/references/reduction-checklist.md](../shared/references/reduction-checklist.md)

若已有 PRD，基于 PRD 产出。

## 工作方式

1. 只覆盖影响评审的页面和状态。
2. 优先表达主流程、异常状态、空状态、权限差异、关键反馈和状态流转。
3. 用原型审查发现文字方案里的遗漏，例如返回、撤回、失败、无权限、空数据和处理后状态。
4. 服务业务评审，不追求炫技或通用组件体系。
5. PRD 已讲清的内容，不在原型里重复堆说明。
6. 假数据保持真实业务感，不伪装成最终文案。
7. 演示控件与真实页面结构分层，不混入正式页面功能。
8. 原型代码应自带基础可用性：响应式布局、可读文字、完整交互状态和清楚的错误/空/加载态。

## 页面本体准入流程

每次新增或修改页面内容前，必须先判断内容属于“业务页面本体”还是“评审辅助信息”。

强制流程：

1. 先问：这是最终用户、后台用户或业务操作人员真实会看到或操作的内容吗？
2. 如果只是解释规则、解释差异、解释为什么、解释切换后会怎样、提示评审关注点，不能放进页面本体。
3. 评审辅助信息只能放进原型摘要、旁注交付物、对话说明或 PRD，不得伪装成页面里的说明卡片。
4. 页面本体里的内容必须能落到明确字段、状态、按钮、表格列、表单项、列表项、空状态或错误状态上。
5. 如果新增内容只是为了“让评审更懂”，默认不进页面；不要做说明卡片、差异卡片、规则卡片、解释卡片。
6. 除非用户明确要求给真实业务用户展示，否则不要把规则说明、题型差异、配置逻辑、状态判断顺序写进页面主体。

## 列表页副文案约束

列表页是扫描和比较界面，不是解释规则的地方。

强制规则：

1. 表格单元格内的副文案只允许承载结构化增量信息，例如状态值、时间、计数、范围、版本、来源、缺失值原因。
2. 禁止在表格副文案里写流程解释、规则解释、原因解释、后果解释或评审提示。
3. 如果副文案只是把相邻列、状态标签或按钮动作再解释一遍，删除。
4. 如果一整列的副文案表达同一含义，先质疑该列或副文案是否必要；默认删除副文案，只保留字段值。
5. 列表页新增或修改后，必须横向扫每一列：同值、重复、解释型、不产生比较价值的内容都要收敛。

提交或回复前必须检查：

- 页面主体中是否出现“说明、规则、差异、切换后、当前只需、不需要、用于评审、为什么、口径”等解释型文案。
- 如果出现，判断它是否是业务用户必须看到的信息；不是则移到摘要或删除。
- 不要用“为了评审清楚”作为保留页面内解释文案的理由。

## 详情页页头约束

详情页、新增页、编辑页的页头必须保持稳定，不承载返回按钮。

强制规则：

1. 页面标题栏默认只放页面标题；确有全局主动作时放主动作，不放普通返回按钮。
2. 不在标题左侧放“返回”按钮，避免和面包屑、底部取消、侧边导航形成重复入口。
3. 取消、返回列表、关闭等离开动作放在页面底部操作区，或由面包屑、目录、侧边导航承担。
4. 新增或编辑多个详情页时，必须横向检查所有详情页页头结构一致。

## 原型辅助层规则

目录、摘要、热区等控件属于原型辅助层，不属于正式业务页面。

强制规则：

1. Web 原型可保留“目录”入口，用于跨页面或页面内状态切换。
2. Web 原型可保留“摘要”入口，用于展示当前页面评审重点，但摘要内容不进入页面主体。
3. 热区只标记明确声明的原型交互点，例如页面切换、弹窗、状态切换。
4. 普通筛选、重置、分页、展示型按钮、展示型链接默认不加热区，也不额外绑定事件。
5. 摘要或热区没有内容时，对应入口应置灰或不可点击。
6. 除非用户特别指定，不为了演示效果给普通控件增加事件，避免浪费原型复杂度和系统开销。

## 评审中修改规则

当用户在原型评审中指出页面状态、字段层级、信息区域规划、业务口径或状态表达混乱时，先暂停改动，不直接替用户拍板改原型。

先输出：

1. 我理解的问题。
2. 建议采用的信息规则或状态口径。
3. 会影响哪些页面、字段、状态或交付物。
4. 需要用户确认的取舍点。

用户确认后再修改原型。只有用户明确说“直接改”“先做一版”“自由发挥”或同等意思时，才可以先动手做一版。

## 低级错误复盘规则

当用户指出重复按钮、无意义说明、词不一致、状态缺反向操作、页面内混入评审解释、普通控件被多余绑定事件等低级错误时，必须先处理错误来源，再继续扩展功能。

强制流程：

1. 先清理当前页面里的同类问题，不只修截图中被指出的那一个点。
2. 判断错误是否来自长期工作流缺口；如果是，必须更新项目 README、原型规范或本 Skill，而不是只在对话中解释。
3. 继续修改前，按新增规则做一次自检，避免让用户重复指出同类错误。
4. 回复用户时只说明已沉淀到哪里和当前清理结果，不写空泛道歉。

## 模块标题约束

同一页面结构中的同一功能区域，模块标题必须固定，不得随着状态、结果或数据变化而改名。

强制规则：

1. 模块标题只表达区域职责，不表达当前状态。
2. 状态差异只能放在状态标签、字段值、说明文案、列表项状态或底部主动作中。
3. 不得把同一模块在不同状态页中分别命名为“考试记录 / 考试结果”“完成条件 / 完成结果”“已完成课程 / 培训课程”等。
4. 如果某个区域职责相同，即使通过、未通过、可重考、不可再考、已完成，也必须使用同一个标题。
5. 如果确实需要不同标题，必须先说明它们承担的是不同页面职责，而不是同一职责的不同状态。

检查方式：

- 同一批状态页横向对比模块标题。
- 先问“这个区域是在表达职责，还是在表达状态”。
- 如果标题里出现结果词、状态词或数量词，优先下沉到标签或字段值。
- 结果态页面尤其要检查：说明区、结果区、课程区、底部动作是否各司其职，不能用标题重复表达状态。

## 页面内说明克制原则

原型页面里的说明文案必须有明确职责，不能为了“怕用户不懂”到处补解释。页面本体不是评审讲稿。

在新增任何说明文案前，必须先执行“页面本体准入流程”。凡是评审辅助信息，一律不进入页面本体。

强制规则：

1. 如果顶部状态、模块标题、字段值、标签、列表项状态或按钮动作已经能表达含义，不再追加解释句。
2. 卡片内优先展示结构化信息，不夹叙述性说明。
3. 同一含义不得同时出现在说明区、结果卡、课程卡、底部动作和右侧补充说明中。
4. 右侧补充说明用于评审解释，不应把评审解释搬进小程序页面。
5. 只有当用户必须知道原因或下一步，且页面其他位置无法表达时，才允许保留短说明。
6. 结果类卡片只放结果字段，不写“你现在应该怎么理解这个结果”的解释。

检查方式：

- 每次新增说明句前，先判断它是否只是解释已有状态。
- 如果这句话能被状态标签、字段值、按钮文案或模块顺序替代，删除。
- 如果同一句话已经出现在右侧补充说明，不再搬进页面本体。
- 优先删掉“当前只需……”“不需要……”“可回看……”这类重复解释，除非它是唯一的操作指引。

## 原型更新登记

当本轮新增或修改原型页面、原型入口、关键状态、交互路径或原型版本时，必须检查项目根目录是否存在 `index.html` 评审目录页。

如果存在，完成原型修改后必须同步在目录页的“更新记录”中登记一条记录，至少包含：

- 日期
- 变更对象
- 一句话变更内容
- 对应版本或状态

登记原则：

1. 只记录对评审追溯有价值的变化，不登记纯格式化、无业务含义的微调。
2. 如果某个原型文件单独升级但整体交付版本未升级，在更新记录中写清对象和版本；不要默认把版本号堆到每个入口按钮上。
3. 如果目录页不存在，不强行创建；在回复中提醒需要补目录页或更新记录。
4. 回复用户前检查：本轮原型变化是否已经被目录页追溯。

## 交接到评审收口

当原型的页面结构、关键状态和交互路径已经基本稳定，而用户反馈集中在页面减法、视觉层级、状态统一、按钮可点击性、同类页面一致性、响应式或目录更新登记时，停止继续在本技能内扩展原型，改用 [../review-prototype/SKILL.md](../review-prototype/SKILL.md) 做评审前收口。

## 输出

输出应至少包含：

- 原型覆盖了哪些页面或场景
- 原型未覆盖哪些内容
- 关键状态说明
- 与 PRD、Brief 或流程图是否存在需要同步更新的差异

## 边界

- 不写技术实现方案。
- 不扩展到设计系统建设。
- 不为了美观而牺牲评审效率。
- 不把原型当成正式开发代码承诺。
- 不使用强风格化、炫技动画或作品集式视觉表达。
