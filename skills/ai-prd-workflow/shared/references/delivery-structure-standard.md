# 交付目录结构标准

## 背景

`ai-prd-workflow` 当前已经对需求澄清、Brief、PRD、原型、规则稿和流程图的阶段顺序有要求，但对“正式交付开始前是否必须先建立固定目录结构”还没有形成显式约束。

这会导致一个典型问题：

- 需求启动时先随手在根目录创建单个 Markdown 文件
- 后续随着 Brief、PRD、原型或流程图增加，再回头补目录结构
- 不同需求之间的目录标准和主入口不一致
- 评审人看到的入口漂移，历史资料和最终资料容易混放

该问题不是单个需求内容问题，而是 `ai-prd-workflow` 顶层治理问题。

## 目标

为所有通过 `ai-prd-workflow` 启动的新需求提供统一的目录结构标准，确保：

- 交付入口一致
- Brief、PRD、原型、流程图和附录有固定落点
- 同类需求目录结构可复制
- 后续新增或迭代产物时不需要反复搬运文件

## 适用范围

适用于所有进入正式交付阶段、且需要落地为可共享需求包的需求。

以下情况默认应建立标准目录结构：

- 需要产出 Brief 或 PRD
- 需要跨人评审或共享
- 预期后续可能继续补原型、规则稿或流程图
- 需要保留过程性材料与最终版入口

## 建议默认结构

```text
需求目录/
├── README.md
├── annex/
├── prd/
├── prototype/
└── flowcharts/
```

## 目录职责

### `README.md`

主入口文件。只负责提供统一、干净的分享入口，不重复承载完整正文。

建议包含：

- 一句话摘要
- 当前状态
- 当前结论
- 主入口
- 评审入口
- 当前待确认
- 建议阅读顺序
- 历史资料说明

### `annex/`

用于放过程性或辅助性材料。

建议包括但不限于：

- `requirement_clarification.md`
- `review_brief.md`
- 治理备注
- 过程记录
- 归档说明

### `prd/`

用于放正式交付正文。

建议包括但不限于：

- `prd_v1.0.md` / `prd_v1.0.html`
- `rules_v1.0.md` / `rules_v1.0.html`
- 评审版正文

### `prototype/`

用于放原型及原型说明。

若当前阶段暂无原型，也建议保留目录，并用 `README.md` 说明未产出原因。

### `flowcharts/`

用于放流程图及流程补充说明。

若当前阶段暂无流程图，也建议保留目录，并用 `README.md` 说明未产出原因。

## 建议工作流要求

后续 `ai-prd-workflow` 顶层 skill 应显式增加以下要求：

1. 一旦确认这是一个需要正式交付的新需求，先检查当前工作区是否已有标准目录结构。
2. 若没有，则先创建标准目录，再开始写 Brief、PRD 或其他交付物。
3. 不建议先在根目录随意落单个 Markdown，再回头搬运。
4. 即使当前阶段暂不需要原型或流程图，也建议先保留目录，以减少后续结构漂移。
5. `README.md` 只作为主入口，不替代正式 PRD、规则稿或原型正文。

## 与现有 skill 的关系

这份文档应作为顶层 workflow 的引用标准，而不是替代 `SKILL.md`。

建议未来在 [`SKILL.md`](../../SKILL.md) 中仅增加简短约束，例如：

- “进入正式交付前，先建立标准目录结构；具体规范见 `shared/references/delivery-structure-standard.md`。”

这样可以保持顶层 skill 正文简洁，同时让结构标准可独立维护。

## 当前状态

当前文档为治理草案，作用是先把问题显式记录到仓库版 skill 中，作为后续更新顶层 workflow 的依据。

它目前只是被记录，还没有自动纳入 `ai-prd-workflow` 的强制执行流程。
