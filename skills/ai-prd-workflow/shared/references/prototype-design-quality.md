# 原型设计质量吸收规则

本文件吸收原独立设计类技能中适合 PRD 原型的部分，用于让 `ai-prd-workflow` 在单一技能内完成“可评审、清楚、专业”的原型交付。

引入这些设计质量规则，不代表 `ai-prd-workflow` 的主目标转向原型设计。主流程仍是需求收口、口径确认和正式交付组织。

这些规则用于补齐 AI 在原型交付中的常见短板：视觉一致性、响应式适配、状态完整性、文案清晰度和边界数据表达。目标是让原型更好服务 PRD 评审，而不是把原型升级为独立设计项目。

原始参考只保留在 [design-skills-archive](design-skills-archive) 中。该目录不是独立技能集合，仅作为按需查阅的设计质量来源。

## 1. 吸收范围

保留并吸收这些能力作为原型内置检查：

- [frontend-design.md](design-skills-archive/frontend-design.md)：吸收反模板化和设计上下文意识，改为服务企业业务原型，不追求强创意视觉。
- [polish.md](design-skills-archive/polish.md)：吸收最终走查，对齐、间距、字体层级、颜色语义、交互状态、表单、图标、空/错/加载态。
- [adapt.md](design-skills-archive/adapt.md)：吸收响应式原则，桌面、移动端、触屏目标、窄屏重排和横向溢出检查。
- [harden.md](design-skills-archive/harden.md)：吸收边界数据检查，长文本、空值、极端数量、错误、禁用、加载、权限不可用。
- [audit.md](design-skills-archive/audit.md)：吸收最低质量维度，可访问性、性能、响应式、主题一致性、反 AI 模板化。
- [critique.md](design-skills-archive/critique.md)：吸收评审视角，视觉层级、信息架构、认知负担、可发现性和状态完整性。
- [arrange.md](design-skills-archive/arrange.md)：吸收布局节奏、分组关系、空间层级和视觉重心。
- [typeset.md](design-skills-archive/typeset.md)：吸收文字层级、可读性、行高、字号和字重一致性。
- [colorize.md](design-skills-archive/colorize.md)：吸收颜色语义、状态色和少量业务信息强调，不吸收装饰性上色。
- [clarify.md](design-skills-archive/clarify.md)：吸收按钮、错误、空状态、表单提示和确认弹窗的清晰文案原则。

以下方向已从归档中移除，不作为 `ai-prd-workflow` 的设计来源：

- 强风格化、炫技、惊喜感、作品集表达。
- 设计系统抽取、组件库治理、项目级设计记忆。
- 独立引导、性能专项、动效专项、简化专项流程。
- 与 PRD 评审目标无关的品牌创意扩展。

## 2. 原型设计上下文

产出原型前先确认或沿用以下上下文；若缺失且会影响判断，提出最少量问题：

- 目标用户和评审对象：业务、运营、产品、客服、管理者或终端用户。
- 使用端：桌面 Web、移动端、小程序、后台系统或多端。
- 场景重点：录入、审核、查询、处理异常、查看状态、批量操作或管理配置。
- 质量目标：只用于内部评审、需要对外演示、还是作为研发理解参考。

不要因为缺少品牌语气就暂停原型。默认采用企业业务系统风格：克制、清楚、稳定、可长期复用。

## 3. 构建阶段要求

`build-prototype` 阶段先保证结构和状态：

- 页面结构应覆盖主流程、关键分支、空状态、错误态、禁用态、加载态和成功反馈。
- 表单、列表、详情、弹窗、筛选、批量操作等控件应接近真实业务使用方式。
- 假数据要有业务真实感，包含长名称、缺失字段、异常状态和边界数量。
- 不把说明文字堆进原型页面；评审说明放在交付说明中。
- 主要交互必须能走通，不能只有静态展示。

## 4. 样式阶段要求

`review-prototype` 阶段按以下顺序处理：

1. 信息层级：主标题、区块标题、字段名、正文、辅助信息、状态标签应一眼可分。
2. 布局节奏：相关内容紧密分组，不相关内容留出分隔；避免所有区块使用同样间距。
3. 组件一致性：按钮、输入框、选择器、表格、标签、提示和弹窗保持统一风格。
4. 颜色语义：主色、成功、警示、错误、禁用、信息提示必须含义固定。
5. 文案清晰：按钮动词明确，错误说明给出原因和下一步，空状态说明可执行动作。
6. 交互状态：默认、悬停、聚焦、激活、禁用、加载、错误、成功都应有可见表达。
7. 图标和视觉细节：图标来自同一风格；不要用装饰图标替代清楚的业务信息。

## 5. 响应式和可访问性

原型至少检查桌面和窄屏两类视口：

- 不出现横向滚动，表格应使用合理的横向滚动、列折叠或摘要卡片。
- 触屏操作目标不小于约 44px，移动端文字不应过小。
- 键盘焦点清楚，表单控件有明确标签。
- 文本对比度足够，错误信息不只依赖颜色表达。
- 长文本、长数字、中文/英文混排、空值和多行内容不会撑破布局。

## 6. 性能和动效

原型不追求性能极限，但不能影响评审：

- 避免大体积无关依赖、复杂动画和无意义图片。
- 状态切换可以有轻量过渡，优先使用 `opacity` 和 `transform`。
- 尊重 `prefers-reduced-motion`，不要使用抢注意力的循环动画。
- 加载态应稳定占位，避免内容跳动。

## 7. 反模板化检查

交付前避免这些常见问题：

- 满屏同尺寸卡片、嵌套卡片、装饰性玻璃态、发光边框、渐变大标题。
- 所有按钮都像主按钮，主次动作不清。
- 大面积深色霓虹、紫蓝渐变、无业务含义的装饰图形。
- 为了好看牺牲信息密度和评审效率。
- 页面像营销落地页，而不是业务评审原型。

## 8. 最终走查

交付前输出或自检：

- 覆盖了哪些页面、场景和状态。
- 哪些状态是演示用假数据，哪些规则来自 PRD 或 Brief。
- 桌面和移动端是否都可读、可点、无明显溢出。
- 是否仍存在影响评审的视觉、文案、状态或适配缺口。
- 是否需要同步更新 PRD 的截图、状态描述或页面说明。
