# clarify-requirement

只做需求澄清，不直接生成 PRD、原型、流程图或技术方案。

## 目标

- 用最少的追问补齐关键缺口。
- 把零散输入整理成可继续产出的结构化摘要。
- 判断需求是否已经足够进入 PRD 阶段。

## 输入

可以接受以下任意一种或多种输入：

- 一句话需求
- 聊天记录
- 会议纪要
- 页面截图
- 样本、案例、数据说明

## 工作方式

1. 先阅读 [../shared/references/context-checklist.md](../shared/references/context-checklist.md)。
2. 只追问会影响方案方向的缺口，不把对话变成问卷。
3. 不重复用户已经明确给出的信息。
4. 如果信息已经足够，直接给出结构化摘要，不强行继续追问。
5. 如果样本会影响判断口径，明确指出哪些样本还缺失。

## 输出格式

输出应尽量收敛为以下四部分：

### 1. 已知信息

- 背景
- 目标
- 用户
- 场景
- 现状
- 成功标准

### 2. 待确认问题

- 只列真正影响方案方向的问题
- 优先列 2 到 5 个

### 3. 结构化需求摘要

用简洁文字总结：

- 问题是什么
- 为什么现在要做
- 谁会使用
- 用户在什么场景下使用
- 成功的判断标准是什么

### 4. 阶段判断

明确给出以下其中一种结论：

- 信息已足够，可以进入 PRD 阶段
- 仍需补充少量信息后再进入 PRD 阶段

## 边界

- 不输出技术设计。
- 不直接拆研发任务。
- 不为了显得全面而追问无关信息。
